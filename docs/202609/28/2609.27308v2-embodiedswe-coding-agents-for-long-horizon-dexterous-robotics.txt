ABSTRACT
We study coding agents for long-horizon, dexterous robotics and ask whether
their solutions can provide scalable supervision for learning general robot poli-
cies. To test this, we develop EMBODIEDSWE-BENCH, a simulation benchmark
for coding agents spanning contact-rich manipulation, deformable objects, and
long-horizon tasks requiring up to half an hour of continuous interaction. We
find that frontier coding agents can solve complex long-horizon tasks and trans-
fer prior solutions across both tasks and embodiments. We also design support-
ing tools that help agents more effectively solve these tasks. However, the re-
sulting solutions require substantial iterative interaction and are typically special-
ized to individual task instances. We therefore introduce EMBODIEDSWE-GEN,
which expands a single solution from coding agent into large diverse trajectories
for training a VLA. VLA performance improves with more generated demon-
strations, and agent-aided diversification improves generalization to held-out task
variations. We also show that a VLA finetuned solely on coding-agent-generated
simulation demonstrations completes a long-horizon task on real robot. Together,
our framework uses coding agents to solve complex robotics tasks and turn veri-
fied solutions into scalable supervision for robot policies.

INTRODUCTION
A longstanding goal in robotics is a generalist robot that can act autonomously in daily life, solving
a wide range of dexterous and long-horizon tasks. Imagine a robot that can construct a house com-
pletely autonomously; this requires months of coordinated work from fine-grained woodworking,
to furniture assembly, to electrical wiring. A true generalist robot could do all of these compo-
nents continuously for days or weeks. Yet current approaches remain far from achieving this goal.
Vision-language-action (VLA) models, for example, learn from demonstrations (Intelligence et al.,
2025; NVIDIA et al., 2025; Team et al., 2025), but collecting such data at scale remains expen-
sive (Tian et al., 2025). Teleoperation requires many human operators and can be difficult to scale.
And learning directly from human video demonstrations can result in mismatches with real robot
embodiments. For precise interactions such as screw threading, tight insertion, or grasping in deeply
cluttered environments, collecting demonstrations can be prohibitively difficult.
Recently, coding agents have offered a new paradigm: they write, execute, inspect, and revise robot
control programs much like human engineers, turning robot programming into an iterative process
of action and reflection. Existing work remains largely constrained to navigation and pick-and-place
tasks (Fu et al., 2026; Mu et al., 2024; Singh et al., 2022; Huang et al., 2023), often relying on
human-designed interfaces such as object-pose queries or macro primitives that constrain the task

This raises a question: can coding agents solve long-horizon dexterous tasks in a way that cre-
ates scalable and transferable demonstration data for bootstrapping generalist policies? We
examine this question in three parts.
First, we build a benchmark of daily-life tasks, EMBODIEDSWE-BENCH, including problems that
take tens of minutes to solve and involve contact-intensive manipulation, deformable objects, liquids,
and cutting. For example, the benchmark tests whether a coding agent can create a solution program
for cutting food, assembling an Ikea table, and packing away tools into a drawer.
Second, we test whether coding agents can create full solutions to the problems in EMBODIEDSWE-
BENCH when given access to the full simulator state. And we find that frontier agents can find
solutions to many of these problems—from 11% success rate on GPT-5.6 Terra to 82% on GPT-
6 Astra. We also show that giving access to additional tools as part of the harness can improve
performance further in some cases. This shows that coding agents could potentially be used to
create precomputed solutions to complex long-horizon problems, with little intervention.
Third, we test whether these coding agent solutions can help bootstrap generalist policies, like
VLAs. We create a hierarchical pipeline, EMBODIEDSWE-GEN, with data augmentation and other
improvements, that creates teacher demonstrations from the coding agent solutions. We find that
VLA success rates improve with the amount of demonstrations from the coding agent pipeline,
and even improve out-of-distribution performance more than baseline domain randomization ap-
proaches. We further demonstrate sim-to-real transfer: a policy finetuned solely on 500 coding-
agent-generated simulation demonstrations completes a four-stage lamp-disassembly task.
Together our work shows a potential path forward for scaling demonstrations and leveraging cod-
ing agents to create optimal solutions to long-horizon, complex problems. To summarize our work
has three contributions: (1) EMBODIEDSWE-BENCH, a benchmark for evaluating coding agents
on long-horizon, dexterous daily-life robotics tasks with realistic dynamics; (2) coding agents as
solvers, with systematic evaluation of frontier agents on robotics tasks; (3) coding agents as teach-
ers, with a hierarchical data engine EMBODIEDSWE-GEN that transforms verified solutions into
large, diverse datasets for VLA finetuning. We discuss related works in Appendix A.

and long-horizon tasks. We describe the environment design and evaluation protocol below; the full
task catalog and additional details are provided in Appendix B.

2.1
ENVIRONMENT DESIGN
We construct 28 long-horizon and dexterous tasks spanning assembly (9), packing (4), puzzle (6),
deformable object or liquid manipulation (4), cutting (2), and locomotion with manipulation (3).
Examples include assembling an Ikea table with four legs, securing a motherboard with seven bolts,
and tying a shoelace half knot. Tasks demand precise physical interactions and execution horizons
of up to half an hour. The benchmark supports five embodiments: Franka, UFACTORY xArm7,
Kinova Gen3, bimanual Franka, and Unitree G1. Some examples can be found in Figure 2.
Task design and reference-solution development are primarily human driven, with coding-agent as-
sistance. Scenes use Isaac Lab, Isaac Sim robot assets, and downloaded, scanned, CAD-derived, or
custom-modeled objects. Agents have access to full simulator states, generic rendering and inspec-
tion tools, and configurable controllers, including operational-space and inverse-kinematics control.
Humanoid locomotion uses a pretrained policy. Appendix B provides implementation details.
2.2
EVALUATION PROTOCOL
Each evaluation run is executed in an isolated Docker container with a preinstalled Python environ-
ment and simulator. The agent receives only a minimal task-specific copy of the benchmark, the
task instruction, and a fresh workspace; all other resources are inaccessible, with network access
restricted to the model API and Python package index. The required deliverable is a Python pro-
gram exposing solve(env) as its entry point. The agent may submit intermediate solutions, and
submissions are also triggered automatically at fixed intervals.
Grading is performed entirely offline to prevent agents from modifying scene code or exploiting the
reward mechanism. Each submission is evaluated in a separate grading environment with identical
scene dynamics, while state-writing interfaces such as set states() are disabled to preserve
physical consistency. A task-specific grader is used. In some tasks, simulator information is used
for grading—for example if an object is in the right place. In others, a human-written rubric is used,
combined with a VLM, to grade the trajectory or subcomponents of the trajectory.

EVALUATING CODING AGENTS AS SOLVERS
Having established the benchmark and evaluation protocol, we study coding agents as robotic task
solvers. Each agent iteratively inspects the environment, executes candidate solutions, diagnoses
failures, and revises its code, optimizing a program rather than the parameters of a learned policy.
We first evaluate frontier coding agents using their standard coding harnesses (Section 3.1), then
examine transfer learning capability across tasks and robot embodiments (Section 3.2), and finally
describe additional tools for long-horizon solving (Section 3.3). We also explore training coding
agents on synthetic robotics tasks. We present the automatic task construction pipeline and prelimi-
nary agentic RL results in Appendix G.

3.1
FRONTIER AGENT CAPABILITIES
Standard-harness performance.
We evaluate six frontier models on EMBODIEDSWE-BENCH:
Fable 5.1, Opus 5, Opus 4.8, GPT-6 Astra, GPT-5.6 Sol, and GPT-5.6 Terra.
Each model uses its native coding harness: the first three use Claude Code, while the latter three
use Codex. The additional long-horizon mechanisms introduced later in Section 3.3 are disabled.
Unless otherwise stated, all experiments follow the protocol in Section 2.2. Each run uses one
NVIDIA RTX 4090 for simulation and a 4-hour wall-clock budget. At each wall-clock budget, we
report the highest graded score achieved by the run up to that point and average across runs (mean ±
standard error). Wall-clock time includes simulation. Results against generated tokens are provided
in Appendix C.
EMBODIEDSWE-BENCH is deliberately designed around complex, multi-stage tasks that require
precise physical interaction and reflect the structure of everyday robotic scenarios. Despite this dif-
ficulty, frontier coding agents make substantial progress within the 4-hour budget, with the strongest
model solving roughly 80% of the benchmark. The remaining failures are concentrated among some
of the most challenging tasks. These tasks are not inherently infeasible: every evaluated task has
been successfully completed at least once by a domain expert working with a coding model. The gap
therefore highlights the difficulty of autonomously discovering successful programs for the hardest
tasks under a fixed interaction budget.

Coding Agent Policies vs Learned Control Policies.
We compare the programmatic policies pro-
duced by coding agents with state-based MLP policies (Tassa et al., 2018) trained through Proximal
Policy Optimization (Schulman et al., 2017) on five assembly and packing tasks, with similar wall-
clock budgets. We consider three reward design mechanisms of increasing supervision: (1) sparse,
using only the progress signals defined by the evaluation rubric; (2) agent-designed dense, where a
frontier coding agent constructs task-specific dense rewards; and (3) expert-tuned, where a domain
expert works together with a frontier model to refine the rewards, hyperparameters, and relevant
environment settings. For the latter two settings, we allow repeated development and tuning over
approximately one week and report the best resulting training configuration. Reward and training
design are performed offline rather than counted against the solving budget. Despite stronger super-
vision and extensive offline tuning, learning tabula rasa with PPO still substantially underperforms
the programmatic policies discovered by coding agents within the evaluated budgets (Figure 5).
Full task selections, reward definitions, hyperparameters, and tuning procedures are provided in
Appendix C.2.
3.2
TRANSFER ACROSS TASKS AND EMBODIMENTS
Verified solutions often provide useful experience for subsequent problems, even when the tasks are
only loosely related: a prior solution can encode reusable task structure as well as embodiment-
specific knowledge, such as reliable grasp configurations, approach poses, or controller settings. We
study this transfer systematically across both tasks and robot embodiments.
We evaluate Opus 5 and GPT-5.6 Sol, with three seeds per configuration. In each transfer run,
the agent receives, in addition to the standard task materials, one read-only file containing either a
verified solution to another task or a verified solution to the same task on a different embodiment.
For cross-task transfer, we compare against otherwise identical runs without this reference. Full task
pairings, run counts, per-task curves, and token-based analyses are provided in Appendix C.
Transfer across tasks.
For transfer across tasks, we select 6 target tasks and pair each with 2
source tasks: a similar source that shares the target’s dominant underlying skill (e.g., threading, card
seating), and a dissimilar source that does not; the exact pairs are listed in Appendix C. Figure 6
shows the results. Hints from similar tasks help the agent solve the target both better and faster; hints
from dissimilar tasks speed up early progress but end at the same final score as the no-hint runs.
Transfer across embodiments.
For transfer across embodiments, we use the same 6 tasks. For
each task, we provide the verified Franka-arm solution as the hint and instruct the agent to solve
the task on two other embodiments: a Kinova Gen3 and a UFACTORY xArm7, each carrying the
Franka Panda hand so that grasping is comparable while the arm kinematics, joint layout, reach, and
control gains all change. As the no-hint reference, we reuse the Franka runs on these six tasks from
the cross-task experiments. Figure 6 shows that solution transfer is efficient and achieves higher
scores than this reference, suggesting that agents reuse task decomposition and scene reasoning
while adapting motion and control to the new embodiment.

3.3
ABLATING ADDITIONAL TOOLS FOR SOLVING LONG-HORIZON ROBOTICS TASKS
Beyond the standard coding harnesses evaluated in Section 3.1, we provide additional tools de-
signed to support long-horizon, physically complex task solving. Full descriptions of these tools are
provided in Appendix C.4. This includes:
• Checkpoint tree. The agent saves reached simulator states together with the programs, logs,
snapshots, and transition annotations that document its progress as a tree of checkpoints. The
agent can go to any previous checkpoints, allowing the agent to revisit earlier decisions without
replaying long prefixes or losing the record of failed attempts.
• Evolutionary search on parameters. For a fixed program structure, the agent specifies tunable
parameters, search ranges, and an objective. The tool runs CMA-ES (Hansen, 2023) over par-
allel simulations initialized from a common starting state, optionally with initial-state jitter to
reduce overfitting, and returns the best parameters found.
• Other supporting tools. We also provide several other supporting tools that we find useful to
the agents: A scene viewer provides snapshots and videos for visual inspection; a sweep tool
compares alternative programs or strategies in parallel; and an assessment log records structured
descriptions of the scene, failures, and suspicious outcomes after each execution.
We evaluate Opus 5 and GPT-5.6 Sol on our full benchmark using the same set up as in
Section 3.1 with tools, and compare with the performance without tools. Each tool run uses two
RTX 4090s rather than one; the second hosts the parallel simulations of the parameter search and
the sweep tool. The results are presented in Figure 6. We can see that both models are able to achieve
better score with the tools, though effect sizes are relatively small. We present detailed results in
Appendix C and some qualitative analysis in Appendix H.

CODING AGENTS AS TEACHERS
Section 3 demonstrated that coding agents are capable of solving complex, long-horizon robotic
tasks through iterative reasoning, execution, and debugging. These successful solutions provide
more than task completion alone: they also contain structured action sequences and reusable inter-
action strategies. We next ask whether such agent-generated solutions can be used as supervision to
train a general robot policy.
4.1
SCALABLE DATA ENGINE
Generating diverse robot trajectories at scale is challenging because a single coding-agent solution
can require hours of wall-clock time and substantial token cost. Purely rule or script based generation
is cheaper, but its diversity can quickly saturate around a narrow regime. We therefore propose an
agent-powered data engine, EMBODIEDSWE-GEN, that expands each verified solution with both
agent-based diversification and standard domain randomization. We show representative examples
of this diversification in Figure 7 and describe the details of our pipeline in Appendix D.

Figure 7: Hierarchical diversification pipeline of EMBODIEDSWE-GEN. Starting from one verified
coding-agent solution, we diversify the scene, strategy, phase, dynamics, and visual to expand
it into a broad set of training trajectories. Higher-level variations modify task structure, solution
behavior, and intermediate-state coverage, while lower-level variations introduce physical, action,
and visual perturbations to improve robustness and diversify execution.
Agent-based diversification.
The agent edits the task and solution code in four ways. (1) Scene:
it varies objects, tools, distractors, and workspace layouts, updating the success condition and so-
lution as needed. (2) Strategy: it changes the order of interchangeable steps, grasp choices, or the
overall task plan, and adds recovery branches such as regrasping a dropped object. (3) Phase:
to cover intermediate states that are rarely visited by end-to-end rollouts, the agent generates
demonstrations that begin partway through a task. It identifies phase boundaries, constructs di-
verse valid simulator states for those intermediate stages, and adapts the solution to complete the
remaining steps from each state. (4) Noise: a single noise scale can be too weak during trans-
port yet too disruptive during precise manipulation. The agent adapts DART-style noise injec-
tion (Laskey et al., 2017) to the task by inspecting a rendered rollout and writing phase-specific
perturbations into the solution code, for example using stronger disturbances during transport and
weaker ones during insertion. These disturbances can trigger the solution’s recovery branches.

4.2
VLA FINETUNING WITH GENERATED DEMONSTRATIONS
We next test whether trajectories produced by EMBODIEDSWE-GEN provide effective supervi-
sion for VLA finetuning. Since several benchmark tasks remain beyond current VLAs, we eval-
uate SmolVLA (Shukor et al., 2025) on a subset of six tasks: clear organic objects,
pen holder, tool packing, bulb, nut thread, and slice. We study two questions: how
performance scales with the number of generated demonstrations, and whether trajectory diversifi-
cation improves generalization. Training details and task-specific evaluation criteria are provided in
Appendix E.
Scaling with generated demonstrations.
We subsample the generated trajectories at 10, 50, 100,
200, and 400 demonstrations per task to finetune VLA and evaluate in distribution, using the same
scene and initial-state distribution as the generated data. Figure 9 shows that task scores and success
rates improve overall with more demonstrations: the mean success rate over the six tasks rises from
18% with 10 demonstrations to 69% with 400, and the mean rubric score from 0.32 to 0.76.
Generalization across diversification pipelines.
We evaluate whether agent-aided diversification
improves generalization. We compare policies trained on equal numbers of demonstrations gen-
erated by our pipeline or a script-only baseline using standard domain randomization, noise, and
small initial-state perturbations. The script-only baseline remains concentrated around the original
task distribution, whereas agent-aided diversification introduces broader variation in scenes, solution
strategies, and initial configurations. Both policies are evaluated on the same held-out test set, which
contains semantically novel task instances and geometric configurations unseen during training. For
example, in a food-slicing task, agent-aided training data may include bananas, carrots, and cucum-
bers in varied placements, while the test set contains unseen object categories, such as bread, chilli,
and zucchini, in previously unseen initial configurations. For each task and experiment setting, we
train on 1000 generated trajectories, and evaluate on 256 out of distribution settings, reporting the
average rubric score over evaluations. Table 1 presents the results. Across all evaluated tasks, VLA
policies trained with agent-aided diversified data consistently achieve better performance on unseen
scenarios than those trained with script-only data.

Having shown that coding-agent-generated trajectories can provide effective supervision for VLA

5
DISCUSSIONS AND CONCLUSION
We introduced EMBODIEDSWE-BENCH, a benchmark of long-horizon, dexterous daily-life tasks
in which the agent writes code directly against the simulator. We find that frontier coding agents
can already solve a wide range of complex tasks from scratch and transfer verified solutions across
tasks and embodiments, though the hardest tasks remain unsolved. Verified solutions then serve
as supervision for robot learning: with EMBODIEDSWE-GEN, we turn each solution into a large,
diverse dataset for fine-tuning a general robot policy. Together, these results show how coding
agents can solve complex robotics tasks and provide scalable supervision for robot policies, with
demonstrated sim-to-real transfer.

RELATED WORK
Coding agents as robot programmers.
A recent line of work has coding agents solve manipula-
tion tasks by operating a human-built interface, which primarily measures how well the agent can
understand the physical world through that interface. CaP-X (Fu et al., 2026) is the reference bench-
mark, with different tiers of API access. In the most assisted tier, the agent has access to ground-
truth simulation states with human-written macros. Other tiers include curated wrappers over vision
models and planners. Some follow-up works keep the interface and vary the loop around it, e.g.,
skill libraries with evolutionary program search (Lu et al., 2026), training-time evolution of policy
repositories (Elmaaroufi et al., 2026), real-robot self-improvement inside human-built reset and ver-
ification modules (Xiao et al., 2026), and tool-calling over frozen planners and VLAs (Galanti et al.,
2026). Results are polarized, with some easy cube tasks almost saturated while several LIBERO-Pro
long-horizon tasks having zero success (Lu et al., 2026). These interfaces bring problems of their
own: each is task-specific, e.g., CaP-X reimplements get object pose per task family, down
to hardcoded object names. The vision-backed tiers inject perception noise that can compound and
make otherwise correct programs fail. These works also treat the agent’s code as the endpoint,
i.e., the deployed policy itself, as opposed to a teacher. We remove human-designed interfaces on
long-horizon tasks and find that frontier coding agents (e.g., Claude Fable 5) already write working
solutions from scratch against Isaac Sim. We harvest these solutions as training data for policies that
fail there.
Long-horizon manipulation.
Long-horizon tasks are a consistent failure mode for robot policies:
VLA policies degrade most on the long-horizon suites of standard benchmarks (Liu et al., 2023; Tsui
et al., 2026), the strongest agentic systems have zero success on several LIBERO-Pro long-horizon
tasks (Lu et al., 2026), and the 2025 BEHAVIOR Challenge was won at 12.4% success rate despite
1,200 hours of teleoperated demonstrations (Larchenko et al., 2025; Bai et al., 2025). Previous
works improve performance of robot policies on long-horizon tasks with both inference-time and
training-time approaches. Inference-time approaches often decompose the task: Gemini Robotics
1.5 interleaves natural-language reasoning with acting to break down multi-step tasks (Team et al.,
2025), (Zhang & Shah, 2026; Kwok et al., 2025) use verifier to select optimal actions through
best-of-N to steering the inference-time performance. Hi Robot puts a VLM planner over a low-
level policy (Shi et al., 2025), and Pigey runs an orchestration loop with explicit memory over
frozen skills (Galanti et al., 2026). Training-time approaches instead supply long-horizon data: π0.5
reaches multi-minute behaviors through heterogeneous co-training (Intelligence et al., 2025), and
InternData-A1’s ablation shows that removing its long-horizon slice hurts pre-training more than
removing pick-and-place entirely (Tian et al., 2025).
Automatic data generation in simulation.
A large body of work automates parts of the simula-
tion data pipeline, but every method multiplies or perturbs something a human first supplied, and
that input caps the horizon of what it can generate. Task and scene generators need a human to
write the task schema, label per-asset keypoints for a hand-built motion planner, define reward tem-
plates for per-subtask RL, or teleoperate seed demonstrations (Wang et al., 2024a; Hua et al., 2024;
Wang et al., 2024b; Nasiriany et al., 2024). InternData-A1 provides evidence that simulation alone
suffices for VLA pre-training and identifies trajectory diversity as possibly crucial to pre-training
quality; yet it produces data by chaining hand-engineered scripted skills under a human-authored
per-task configuration (Tian et al., 2025). Related works extend the recipe in different directions, in-
cluding synthesizing tasks together with executable success checks (Wang et al., 2026a), co-training
on neurally generated trajectories (NVIDIA et al., 2025), or rolling trajectories out inside learned
world models (Guo et al., 2026).
Prior demonstration synthesis pipelines have similar dependence on human demonstrations: the
MimicGen family turns ∼10 teleoperated demonstrations per task into thousands by SE(3)
transform-and-replay of recorded segments with success filtering (Mandlekar et al., 2023; Jiang
et al., 2025; Garrett et al., 2024); a broad family of methods synthesizes new demonstrations by
varying human-provided seeds (Xue et al., 2025; Zhang et al., 2026; Wang et al., 2025; Yu et al.,
2025; Ravan et al., 2026; Kim et al., 2026; Zhu et al., 2026); QDTraj applies quality-diversity to tra-
jectories over a low-dimensional, human-parameterized pose genotype (Kappel et al., 2026). Some
recent works begin to hand scene and environment generation itself to agents (Ranawaka et al., 2026;
Wang et al., 2026b; Kang et al., 2026).

B.2
ENVIRONMENTS
Simulation settings.
Physics are simulated with PhysX through Isaac Lab, using a 10ms time
step and the TGS solver by default; the four deformable-object tasks (tshirt, dumpling,
shoe knot, latte) run on Isaac Lab’s Newton backend instead. Scenes may override these
defaults to accommodate their contact geometry.
In particular, the threaded-assembly scenes
(nut thread, allen bolt, pc motherboard, and ikea table) model explicit thread en-
gagement using signed-distance-field collision meshes and therefore use higher solver iteration
counts and larger GPU contact buffers. Embodiment-specific presets may further adjust these set-
tings. Each control step advances the simulation by several physics substeps, as determined by the
controller’s decimation. Scene-specific mechanics, such as the syringe’s plunger-liquid coupling,
are updated at every substep.
Randomization.
Each scene defines a distribution over reset conditions, and each graded episode
is sampled from that distribution. For example, in coffee, the capsule and mug are initialized at
their tray slots with ±2cm of horizontal jitter and random yaw; the brew duration is also sampled.
In pen holder, the number of pens present is sampled per episode, and the holder and all present
pens are placed with ±4cm of horizontal jitter and random yaw. Each scene records its randomiza-
tion ranges in its configuration. Agents develop against a fixed seed but are explicitly informed that
grading uses different initial conditions.
Assets.
Robot models are vendored from the Isaac Sim asset library and patched locally as needed.
For example, the stock xArm7 gripper attachment declares a second articulation root, which we
remove in our copy. Task objects are downloaded, scanned, or hand-modeled assets included with
the benchmark. Offline vendoring scripts derive asset-specific constants, including grasp bands, rest
heights, and mouth frames. The resulting values are recorded in the corresponding scene source.

C.2
RL POLICY BASELINE DETAILS
This section details the RL policy baselines compared against programmatic policies in Section 3.1.
The baselines share one training and grading stack; the three conditions differ only in who writes
the reward and whether the environment is adapted to it.
Tasks.
We train on five single-arm Franka tasks: bulb, nut thread, slice, pen holder,
and tool packing. These span the assembly, cutting, and packing suites and use the same regis-
27


Preprint.
tered presets as the agent runs. The tasks are drawn from the easier tiers of EMBODIEDSWE-BENCH
(Table 3) and have relatively few rubric stages, so they favor RL: each rubric has two or three stages,
and the first stage is a pick in every case. Performance is graded with the same rubric score as the
agent runs. In addition, we manually inspect every graded trajectory for reward hacking and deduct
the score of any stage that was reached without genuinely performing it.
Observation and action.
The observation is the concatenation of the flattened full simulator state
returned by the environment’s get states() (in environment-local coordinates, with actuator
setpoints and controller state dropped), the end-effector pose and velocity, and the previous action.
We additionally apply PPO’s running observation normalization. Actions are normalized to [−1, 1]
and mapped affinely onto the preset controller’s command range; finger dimensions map to per-
finger position targets in metres.
Reward construction.
Across all RL conditions, the per-step reward combines a task-specific
potential ϕ(st) ∈[0, 1] with a binary success bonus:
rt = (ϕ(st) + 1[successt]) ∆t,
where ∆t denotes the control period. Success and the stage-progress curves reported in our analysis
are determined by the task grader. Episodes use a fixed horizon and do not terminate upon success.
The three RL conditions differ in how the potential ϕ is constructed.
• Sparse. ϕ is given by the grader’s weighted rubric progress. This provides RL with a privileged
signal that is never exposed to the coding agent. Because the policy can occasionally increase
rubric progress without actually completing the intended stage—for example, by knocking the
bulb upward and transiently satisfying the lifted height threshold—we manually inspect RL
rollouts for reward hacking. Any spuriously triggered stage is removed from the reported score.
We apply this correction consistently across all evaluation within this test.
• Agent-designed dense. A frontier coding agent proposes a task-specific dense potential itself,
written as a weighted sum of stage terms over the scene’s public accessors (part poses, tolerances,
and the hand pose), and iterates on it offline for about one week against training runs. Table 15
lists the final reward proposed by the agent after these offline iterations.
• Expert-tuned. A domain expert working with a frontier model iterates on the reward, the envi-
ronment, and the training hyperparameters for about one week, with the goal of reaching as high
a rubric score as possible. Table 16 summarizes the reward terms and the weights used in train-
ing, Table 17 summarizes the environment changes for each task, and Table 18 summarizes the
fine-tuned training hyperparameters.
Algorithm and hyperparameters.
We use PPO (Schulman et al., 2017) as implemented in
rsl rl (Rudin et al., 2022) with the Isaac Lab manipulation defaults, uniform across tasks: 1,024
parallel environments, actor and critic MLPs with hidden sizes (256, 128, 64) and ELU activations,
running observation normalization, initial action noise standard deviation 1.0, 64 steps per environ-
ment per iteration, 4 passes over each collected rollout batch with 4 mini-batches per pass, clipping
parameter 0.2, GAE with γ = 0.99 and λ = 0.95, value-loss coefficient 1.0, adaptive learning rate
starting at 10−4 with a KL target of 0.016, gradient-norm clipping at 1.0, and no entropy bonus. The
sparse and dense conditions use these values unchanged; the expert-tuned condition overrides them
per task (Table 18).
Evaluation protocol.
Each run trains on a single RTX 4090, and every condition is trained with
three seeds per task. Checkpoints are saved at every whole hour of training; each is exported as a
TorchScript policy and graded via the standard evaluation protocol described in Section 2.2. Each
grade takes 32 trials with a fixed evaluation seed, and the average is reported. We additionally
manually check each recorded grading trajectory and correct the score for reward hacking.

Evolutionary search on parameters.
Solution programs often contain constants such as rotation
angles, torque limits, and per-step insertion increments. An agent may discover a suitable program
structure but spend substantial time tuning these constants through sequential reruns. We therefore
provide an evolutionary search tool that optimizes parameters while keeping the program structure
fixed.
The agent specifies the parameters to search, a range for each, and an objective to minimize. For
example, when seating a leg, the objective can be the remaining insertion depth plus the lateral offset
from the slot. The tool constructs a batched instance of the task with 512 parallel environments by
default, initializes every environment at the state from which the search begins, and runs CMA-
ES (Hansen, 2023) over the declared ranges. Parameter specifications support floating-point and
integer ranges, logarithmic scaling, and categorical choices.
The agent’s current parameter values are included as a candidate in the first generation, so the best
evaluated candidate is no worse than this baseline on the search objective. To reduce overfitting to
a single starting configuration, the tool can jitter the starting states of named objects independently
across environments and average each candidate’s objective over several jittered repeats. By default,
the search runs for eight generations. It returns the best parameters found, a per-parameter sensitivity
estimate, and a warning whenever a best value lies at the boundary of its declared range.

D
EMBODIEDSWE-GEN DETAILS
In this section, we describe the details of our data engine EMBODIEDSWE-GEN. The engine has
three stages: diversification, batched generation, and automatic verification and augmentation. Its
core is offline diversification: a coding agent expands each verified solution along five levels, propos-
ing semantic variations together with the corresponding code or state perturbations. These variants
are then composed and rolled out in massively parallel simulation to generate trajectories at scale.
Finally, failed or low-quality trajectories are filtered out, while retained trajectories are augmented
with additional supervision, such as task progress and natural-language descriptions of the current
situation and intended goal. Much of this annotation can be derived directly from the solution pro-
gram and simulator state through scripted processing, making it substantially cheaper than labeling
each generated trajectory post hoc with humans (Lynch et al., 2023; Sermanet et al., 2023) or foun-
dation models (Xiao et al., 2023; Zawalski et al., 2024). Section D.1 describes the five levels of
hierarchical diversification; Section D.2 describes how a generation run is orchestrated and verified;
Section D.3 describes what a run delivers.
D.1
DIVERSIFICATION LEVELS
Scene.
The agent edits the scene code and task configuration by varying objects, tools, or
workspace conditions. Examples include replacing the knife used for cutting, swapping the food
item to be diced, adding more objects to a tabletop-cleaning task, introducing distractors or ob-
stacles, or rearranging the workspace. When necessary, the agent also updates the corresponding
success condition and solution strategy. Edits that would change the task’s contact-critical mechan-
ics (thread geometry, insertion channels, fastening) are not permitted, and the delivered solve must
still succeed in the new scene.
Strategy.
The agent directly modifies the solution code to produce alternative strategies at three
levels of granularity: solver parameters, such as applied force or clearance; local decisions, such
as grasp locations or the ordering of interchangeable steps; and qualitatively different plans that
change the overall task strategy. The agent may also introduce recovery branches to recover from
off-nominal states created by noise perturbations, such as returning to a grasping phase after an
object is dropped. Only the latter two count as new strategies for the purpose of the strategy gate
(Section D.2); parameter changes on the same motion are kept as arguments of an existing solution.
Phase.
As tasks become longer, agent-generated solutions naturally decompose into multiple
phases. However, successful rollouts from the default initial state typically cover only a narrow
subset of the intermediate state space. We therefore ask the agent to identify phase boundaries,
propose diverse valid initial conditions for each intermediate phase, and solve directly from those
states, substantially expanding coverage of states that are rarely encountered in end-to-end rollouts.
Concretely, the agent writes one initial-state builder per phase and a version of the solution that can
be entered at any phase; at generation time the builder constructs the initial state and the solution
runs from there to completion under the task’s grader.
Dynamics.
We diversify dynamics in two ways. First, we randomize physical parameters such as
mass, friction, and contact properties. The agent declares, once per scene, the ranges over which
these parameters may vary (with the nominal values reproducing the original scene); at genera-
tion time each parallel environment draws its own values. Second, we perturb the executed actions
to induce local trajectory variation, using either small DART-style noise (Laskey et al., 2017) at
each step or larger disturbances applied over short intervals. Which perturbation to apply where
is decided by the agent: it is shown a rendered episode of the task, identifies the phases in which
the motion is free (transport, approach) and those in which it is tolerance-critical (grasping, mat-
ing, insertion), and writes a per-phase disturbance into the solution through a dedicated argument,
env.step(action, noise=·). The recorder logs the clean command and executes the per-
turbed one. For position-mode controllers the clean command is the training label, so labels remain
unperturbed while the recorded trajectory shows the recovery; for torque-mode controllers the label
is the achieved next-step joint position, which does reflect the perturbation (Appendix D.3). The
perturbation is scaled by a pipeline-controlled factor that is zero during authoring and verification
34


Preprint.
and non-zero only during the dynamics harvest. These perturbations can produce off-nominal states
and invoke the recovery behaviors introduced at the strategy level.
Visual.
We diversify visual appearance by varying camera parameters, lighting, textures, and
backgrounds. Because these changes do not affect the underlying dynamics, they can be applied
offline to recorded trajectories at rendering cost only. The agent declares, once per scene, the cam-
eras and the ranges of the render-only parameters (lighting intensity and color temperature, table
and background materials, object albedo where it does not carry task-relevant identity); appearance
that the grader or the task depends on is not randomized. Rendering is then fully script-driven: each
verified trajectory is re-rendered under several draws from these ranges through the scene’s cameras.
D.2
GENERATION AND VERIFICATION
Input and trajectory targets.
A run starts from the task’s environment preset and a verified so-
lution folder containing solve.py and its supporting modules. It first obtains one successful
nominal trajectory, then expands the accepted set through scene, strategy, phase, and dynamics di-
versification. Collection targets vary across tasks; they do not specify the number of distinct scenes,
strategies, or phases. Each set contains the preceding set in full. The visual stage renders the ac-
cepted trajectories under multiple appearance settings, producing additional dataset episodes.
Variant organization.
The run maintains its own copies of the scene, grader, and solution code.
Variants are organized by scene, strategy, and, when applicable, starting phase. A scene variant
contains its scene and grader; a strategy variant supplies a solution for a scene; and a phase variant
supplies initial-state builders and a solution that can start at an intermediate phase. We call a runnable
combination of scene, strategy, and optional starting phase a cell. Recorded trajectories identify their
source cell and the fingerprint of its code at recording time.
Initial checks.
Before diversification, the input solution must succeed in a single environment and
pass the replay check described below. It must also complete a batch of 512 parallel environments
with at least one success that passes replay at the same batch size. Failure of the single-environment
check starts an agent session to repair the solution; failure of the batched check starts a session to
adapt it for parallel execution. These checks and any required sessions share a 12-hour time budget.
Acceptance and selection.
At each of the scene, strategy, and phase stages, the agent creates and
tests variants until the trajectory target is met. A stage must introduce at least one new cell, and
every new cell it retains must produce at least one successful trajectory that passes replay. Newly
recorded trajectories count only if their source code is unchanged since recording; an edited cell
therefore needs new successful recordings. Previously accepted sets are retained unchanged when
later stages edit the source code.
Once the acceptance conditions are met, the orchestrator retains the preceding set and fills the re-
maining places by taking trajectories in turn from the available cells, giving priority to cells intro-
duced at the current stage. Byte-identical trajectory files count only once, and newly created cells
with code identical to an existing cell are removed. These checks reject exact duplicates; the au-
thoring instructions specify the intended differences between strategies. This selection procedure
distributes the available places across working variants instead of filling them from a single prolific
solution.
Replay verification.
A recorded success is accepted only if it passes an open-loop action replay
check. The checker rebuilds the recording batch with the same scene, number of parallel environ-
ments, seed, and per-environment physical parameters. It restores the recorded initial states and
controller settings, including gains, control period, nullspace posture, gripper stiffness, and any
changes to these settings made during execution. Changes are reapplied at their recorded steps.
The checker then replays the recorded action sequence without running the solution program and
requires the task’s grader to report success again.
Replay processes the whole recording batch together, keeping each trajectory in its original en-
vironment slot to preserve the batch configuration. A failed replay excludes the trajectory. Dur-
ing recorded execution, solutions are required to affect the world through env.step; direct state
35


Preprint.
changes, external forces, and separate drive commands would introduce effects outside the recorded
actions. Initial-state builders set up a phase before its rollout begins.
Dynamics collection.
An agent session adds action perturbations to the solutions represented in
the phase set and supplies physical-parameter ranges for the base scene. Before collection, the
orchestrator checks the base solution using two 512-environment batches with the same seed and
physical-parameter draws: one without action perturbations and one with them. Acceptance requires
declared physical-parameter ranges, use of the noise argument, at least one success in the clean
batch, a positive fraction of perturbed steps, and at least one perturbed trajectory that succeeds and
passes replay. The result is cached for that code fingerprint.
After this check, scripted batches generate additional trajectories from the cells represented in the
phase set, with physical and solution-parameter sampling and action perturbations enabled. Collec-
tion prioritizes cells with fewer accepted dynamics trajectories. Successful recordings are replay-
checked after each batch. A cell that produces no replay-verified success and has contributed no
earlier dynamics success is removed from further collection. The final dynamics set retains the
phase-set trajectories and adds further trajectories selected in turn across the contributing cells.
Visual rendering.
Every scene represented in the dynamics set must declare its cameras and
visual-parameter ranges. An agent session supplies missing declarations or repairs declarations that
fail a short rendering check. The rendering queue contains trajectory-appearance pairs: the accepted
trajectories at nominal appearance and the same trajectories under sampled appearance settings.
The sampled passes also vary external camera poses. Each pass renders the declared camera views,
and the nominal-appearance pass is processed before the additional appearance passes. Frames are
generated by restoring recorded simulator states; physics is not re-simulated.
Agent sessions and time limits.
Each diversification stage has a separate 12-hour time budget,
covering agent work, simulation, replay checks, and rendering. A session runs one coding-agent
process with a stage-specific brief, the run’s working directory, and access to the simulator. Scene,
strategy, and phase authoring sessions may use the remaining stage budget; individual repair, paral-
lelization, perturbation, and visual-setup sessions are capped at 120 minutes. Trajectories generated
during agent testing are eligible for selection under the same acceptance rules.
During a session, the orchestrator checks the recorded metadata every five minutes. When the meta-
data indicates that the stage requirements are met, it ends the session and performs the full accep-
tance check. If further work is needed, the next session continues from the existing files and notes.
A run stops if a stage cannot finish within its time budget, and reports the failed stage.
Execution and recovery.
In our experiments, each run uses a node with one RTX 4090 for the
simulator, agent process, and orchestrator. The run periodically saves its code, records, and required
trajectory files to durable storage. Restarting a run resumes from this saved state without resetting
its time budgets. Replay checks interrupted by a time limit leave their pending trajectories ineligible
for selection. If the language-model endpoint remains unavailable for ten minutes, the run pauses;
paused time does not count toward the stage budget.
D.3
DELIVERED DATASET
Each generation run delivers a collection of accepted trajectories and their rendered observations.
Dataset construction follows the five diversification levels described above, while the number of
trajectories contributed by each level and their relative proportions vary across tasks. The hierar-
chy provides an organizing framework for generation, without prescribing a uniform allocation of
demonstrations to each level. The policy-learning experiments in Section 4.2 evaluate increasing
dataset sizes assembled through this framework; they do not isolate the contribution of individual
diversification levels.
For policy training, trajectories are converted to the LeRobot format at the recorded control rate.
Visual observations come from the rendered camera views. Proprioceptive observations contain arm
joint positions and gripper closedness. Training actions are commanded joint targets for position-
mode controllers and achieved next-step joint positions for torque-mode controllers; the raw con-
troller command is retained separately. The latter targets describe the motion actually achieved, in-

Different appearance versions of the same physical trajectory share its state and action sequences.

VLA TRAINING AND EVALUATION DETAILS
This section describes the datasets, model, finetuning recipe, and evaluation protocol behind the
policy-learning results in Section 4.2.
Dataset construction.
For each task, we start from one verified coding-agent solution and gener-
ate demonstrations using EMBODIEDSWE-GEN. Every accepted trajectory passes the task grader
and the open-loop replay check. The datasets combine task-dependent contributions from the five
diversification levels, and we evaluate training sets containing 10, 50, 100, 200, and 400 episodes
per task. For the generalization experiments, we construct training sets of 1,000 trajectories for each
diversification setting. The agent-aided setting uses EMBODIEDSWE-GEN to vary scenes, solution
strategies, and initial configurations, while the script-only baseline uses standard domain random-
ization, noise, and small initial-state perturbations. The control rate follows the registered task
configuration and ranges from 15 to 60 Hz across tasks. Trajectories are converted to the LeRobot
format.
For the data-scaling experiments, we downsample each dataset into nested random subsets of
episodes. We shuffle the episode indices once with a fixed seed and take the first n episodes for
each subset size, so every subset contains all smaller ones. Normalization statistics are computed
once on the full dataset and shared by all subsets, so that subsets differ only in the episodes seen
during training.
Observations and actions.
The policy observes the RGB cameras declared by each scene at 480×
640 resolution. Every scene provides a wrist camera and one or two fixed cameras, such as a front
view together with a side or overhead view. The proprioceptive state is 8-dimensional, consisting
of the seven arm joint positions and gripper closedness. The language instruction is the scene’s
goal sentence. Actions are 8-dimensional joint targets at the scene’s control rate, following the
label convention in Appendix D.3. Following SmolVLA’s input format, images are letterboxed to
512 × 512, state and action vectors are zero-padded to 32 dimensions, and the scene’s cameras are
mapped onto the pretrained model’s three camera slots, with any unused slot masked as missing.
Model and finetuning.
We finetune SmolVLA (Shukor et al., 2025) from the public
smolvla base checkpoint, a 450M-parameter model that pairs the first 16 layers of a
SmolVLM2-500M vision-language backbone with a flow-matching action expert. The model pre-
dicts chunks of 50 actions, which spans 3.3 s at 15 Hz and 0.8 s at 60 Hz. We keep the vision encoder
frozen and train the language-model layers together with the action expert.
All runs use the same recipe. We train for 100k steps with batch size 64 using AdamW with learning
rate 10−4, betas (0.9, 0.95), weight decay 10−10, and gradient clipping at norm 10. The learning
rate warms up over 1k steps and then follows a cosine decay to 2.5 × 10−6 at step 100k. We
save checkpoints every 20k steps and evaluate the final checkpoint. Intermediate checkpoints with
a partially decayed learning rate performed substantially worse in preliminary runs, so we do not
report them. Each setting is trained with three random seeds.
Evaluation protocol.
Policies are evaluated closed-loop in the same simulator used for data gen-
eration. At each replanning step, the policy predicts a 50-step action chunk, of which the first 10
actions are executed before the policy is queried again. For the data-scaling experiments, scene
and physics settings are pinned from the training dataset, physical parameters take their nominal
values, and each policy is evaluated on 32 episodes sampled from the scene’s reset distribution (Ap-
pendix B). For the generalization experiments, policies are evaluated on 256 held-out configurations,
covering semantically novel task instances and geometric configurations unseen in either training
dataset. Evaluation seeds are disjoint from those used for data generation and paired across policies
within each experiment. Episodes in which the simulator enters a degenerate contact regime, such as
a bulb wedged in the socket rim that stalls the physics solver, are terminated and counted as failures
rather than re-sampled. We report success rates and rubric scores for the data-scaling experiments
(Table 21) and mean rubric scores for the generalization experiments (Table 1), aggregating results
over three training seeds.

SYNTHETIC ROBOTICS TASKS CONSTRUCTION AND CODING-AGENT

G.1
SYNTHETIC TASK CONSTRUCTION
Robotics simulation tasks provide a natural training environment for coding agents: outcomes are
verifiable in the simulator, and multi-stage tasks come with well-defined partial credit. However, no
existing resource provides such tasks at training scale. The closest, CaP-Gym (Fu et al., 2026), offers
an evaluation harness rather than a training corpus. We therefore design a pipeline that scalably
constructs new simulation environments from seed tasks, following the seed-and-mutate recipe of
automated problem synthesis for coding agents (Zhou et al., 2025; He et al., 2026).
Seed task selection.
An agent asked to propose a task with no anchor gravitates toward similar
patterns (Zhou et al., 2025), so we start every construction by sampling a seed task from Robo-
Verse (Geng et al., 2025), which aggregates tasks from many existing benchmarks. We sample at
the task-file level and exclude locomotion and whole-body families. This leaves a deduplicated pool
of 194 distinct manipulation tasks spanning RLBench (James et al., 2019), LIBERO (Liu et al.,
2023), ManiSkill (Mu et al., 2021), CALVIN (Mees et al., 2022), robosuite (Zhu et al., 2025), and
others. The seed is handed to the agent as a reference only, and the new task is implemented from
scratch in our own task format.
Task construction.
The agent freely chooses how to mutate the seed task, including its objective,
objects, and constraints, while ensuring that the new task is strategically different from its seed.
This means that the solution code requires a different plan and code structure, not just different
parameters or minor changes.
After authoring the scene, the agent writes a teleport solution to the task, i.e., a solution written as
if any object could be teleported to any place. This is significantly easier to write than a real-robot
solution, while still useful for ensuring the legitimacy of the constructed task: teleportation handles
only transport, while load-bearing interactions still go through the simulator’s contact dynamics. For
example, to thread a nut onto a bolt, the solution teleports the nut to just above the bolt, then presses
and twists it down the thread with applied forces until the scene reports success. This certifies that
the interactions the task requires are physically achievable in the scene.
The agent must also account for the embodiment when designing the task. Our coding-agent training
focuses on manipulation with a Franka arm, so beyond obtaining a working teleport solution, the
task construction agent must ensure that a Franka arm, and more generally the target embodiment,
can actually manipulate the objects in the way the task requires. After the teleport solution works,
the agent writes the rubric for the task based on that solution. To check the rubric’s legitimacy, the
agent writes a suite of rejection tests. In each test, the agent specifies a scene state to be rejected,
teleports the scene into exactly that state, and asserts that the rubric rejects it. The agent also writes
a task description for each task.
Validation and acceptance.
We validate each task through six checks: (1) rerun the agent-
authored rejection tests and verify that bad states are correctly rejected; (2) verify that the null policy,
which takes no actions, scores 0 under the constructed rubric; (3) check that scene randomizations
vary across seeds and that the scene settles without numerical blow-ups; (4) verify that the rubric’s
score is non-decreasing throughout the teleport solution; (5) continue simulation after success first
triggers and require success to persist, rejecting fly-through successes; and (6) use an LLM judge
to assess task novelty, solution legitimacy, and task-description clarity. The judge checks whether
the constructed task is strategically different from its seed, whether the teleport solution genuinely
solves the task rather than exploiting environmental loopholes, and whether the task description is
sufficiently clear to support solving the task.
The generated environments currently serve only coding-agent training, since they have not gone
through rigorous visual and physical validation and may carry artifacts such as interpenetrating
geometry. These are tolerable for coding-agent training, where rewards are computed from simulator
states, but not for VLA training, which consumes rendered frames.

TRAINING SETUP AND RESULTS
Training results.
We train Seed-2.1-Lite with turn-level PPO on 400 environments produced
by the pipeline above. Figure 20 shows the training results. Mean task reward roughly doubles, from
0.09 to 0.18, and the success rate rises from 2.7% to 7.5%. The gains arrive in two phases. During
the first 100 steps the task reward is nearly flat while the format penalty shrinks from −0.14 to
−0.06: the agent learns to finish episodes cleanly and to reason more briefly. Task reward begins to
rise only after step 120, once penalties are mostly gone; over the same period the average episode
shortens from 61 to 39 turns. Comparing steps 1–60 with steps 121–180, 31 environments improve
by more than 10 points in success rate. The reward standard deviation across episodes grows from
0.20 to 0.29 over the run, so the learning signal is not saturating at the cutoff. These dynamics
indicate that the generated environments provide a learnable, verifiable training signal for coding
agents. We compare trajectories before and after RL training in Appendix H.6, illustrating what the
agent learned to better solve robotics simulation tasks. External restrictions interrupted the project
before held-out evaluation could be conducted. We therefore leave generalization of the post-trained
agent to unseen tasks for future work.

Agent interface.
The coding agent executes Python programs in a persistent Isaac Lab session,
with Python variables and simulator state preserved between calls. It can inspect the benchmark
source and receives execution logs and task-success feedback. A separate vision-language model
describes the initial scene and subsequent changes from fixed-camera images; the coding agent
receives these descriptions as text. The arm uses operational-space control.
Episodes.
The agent receives the task description, robot configuration, and interaction rules, then
works without human intervention. It may reset the environment or re-home the arm, while direct
object-state edits, external force injection, scene modification, and scorer tampering are prohibited.
Each episode allows at most 120 agent turns and 8,192 generated tokens per turn. It ends when the
agent submits its final response or reaches a turn or token limit.
Reward.
The reward is the final task rubric score in [0, 1], deducted by penalties for formatting
errors and hacks identified by an LLM judge, such as scorer tampering. The total deduction is
capped, with a higher cap when tampering is detected. Episodes that exhaust their budget are scored
using the simulator state at termination.
RL algorithm.
We use PPO with a learned critic and generalized advantage estimation (GAE).
GAE uses γ = 1, with λ = 0.95 for actor advantages and λ = 1 for critic targets. The lower and
upper PPO clipping parameters are 0.3 and 0.35, respectively, with a dual-clip parameter of 2. We
use no KL penalty or entropy bonus.
Rollouts are collected asynchronously. We apply importance-sampling corrections truncated at 2 to
tokens generated by earlier policy versions, and exclude episodes whose policy weights are more
than 16 training steps old.
Optimization.
Each training step uses a batch of 128 episodes and performs one gradient update
over the full batch, with the loss averaged over tokens. Both actor and critic use Muon, with learning

rates of 2.7 × 10−6 and 3.5 × 10−6, respectively, five linear warmup steps, and weight decay 0.1.
The critic is trained alone for five steps before actor updates begin.

LIMITATIONS AND FUTURE DIRECTIONS
In this section, we discuss the limitations and potential future directions of our work.
Coding agents on dexterous hand tasks.
EMBODIEDSWE-BENCH covers a wide range of em-
bodiments, but many others remain, such as dexterous hands with more fingers and joints. Whether
and to what extent coding agents can control such embodiments, and how to guide and train them to
do so, remains an open research problem.
Boundary of coding-agent-to-robot distillation.
Our synthetic task construction, solution gen-
eration, trajectory diversification, and VLA training components could together form a pipeline for
distilling coding-agent capabilities into robot policies. However, we have not yet run this pipeline
end to end to study how much of the coding agent’s capability it can transfer to robot policies.
Moreover, our environment generation pipeline does not optimize the visual quality of the generated
scenes. This matters less for coding-agent training, where rewards are computed from oracle states
and the rendered scenes need only roughly convey what is happening. For robot training, however,
the divergence between generated and real scenes, and the need to guarantee that generated scenes
are physically sound, become much more important. Another interesting question is the best use of
the generated data for extremely complex tasks, e.g., for pre-training, for mid-training, or for RL /
behavior cloning. We leave these as directions for future work.
Training coding agents to better ground in visual observations.
In Appendix G, we trained
a text-only model due to limited resources and because videos, even when subsampled into a few
frames, consume significant context length. How to train coding agents to better ground their code
and actions in visual observations — understanding the scene, tracking progress, and planning ac-
cordingly — is left as a future direction.
Held-out evaluation of the trained agent.
Appendix G reports the training dynamics of RL
post-training on the synthetic tasks. Due to computational resource constraints, we were unable
to evaluate the trained checkpoint on held-out tasks before submission. The training curves and the
qualitative analysis in Appendix H suggest genuine behavioral improvement rather than degenerate
reward exploitation, but quantifying these gains on held-out generated environments, and ultimately
on EMBODIEDSWE-BENCH itself, is the most direct next step for this part of the work.
